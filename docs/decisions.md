# Decisions

The decision log. It lists the decisions that hold. Every entry can come
back for review. The [Roadmap](roadmap.md) names the milestone of a decision
that the code does not implement yet.

## Principles and scope

| # | Decision | Reason |
|---|----------|--------|
| D1 | Rust and Smithay for the core | Smithay is a library without policy, proven in niri and cosmic-comp. Rust is safe when agents change the system live. |
| D2 | Everything is a plugin | Maximum flexibility and a small core. |
| D3 | chora 1.0 is a daily driver with a stable, versioned API; until then, the API changes without notice | A stable API needs real use first. No compatibility code before 1.0. |
| D4 | Reuse before writing; check alternatives for every decision | Little code to maintain. |
| D5 | One vocabulary, defined in the [Glossary](glossary.md) | One language for people and agents. |
| D6 | Inventory and agent memory form a separate layer, not part of the core | The platform stays neutral. |
| D7 | The name is chora, always in lowercase | See [Vision](vision.md#the-name). |
| D8 | The core is GPL-3.0-or-later; code under GPL-3.0-only stays out | The core can then reuse code from Pinnacle and niri. |
| D9 | English for code and documentation | The documentation is public. |

## Core

| # | Decision | Reason |
|---|----------|--------|
| D15 | Build on Smithay; copy from Pinnacle, niri and anvil; no fork | A fork of Pinnacle keeps less than half of its code. See [Alternatives](alternatives.md#pinnacle-code-review). |
| D16 | Pin a Smithay git revision | No Smithay release since 0.7.0. All major users track git. |
| D17 | A scene renderer of chora on GLES 3, on the GL context of Smithay's `GlesRenderer`; GLSL shaders | Smithay's render elements are axis-aligned rectangles. A renderer of its own draws the full 4x4 model and keeps textures between frames. wgpu has no usable dmabuf path for a compositor. |
| D18 | Six node kinds: group, surface, rect, image, shader and text | Widgets come from Wayland clients. An image node shows a PNG asset, for example a window border, without a client per window. A shader can read another node as a texture. A text node lets plugins and agents label a HUD without a client or a rendered PNG. cosmic-text does the shaping and the font fallback, so the node stays small: text, font family, size, color and maximum width; no editing and no rich text. |
| D19 | Transforms are 4x4 matrices; the scene is 2.5D: planes in perspective, meshes and fragment shaders. A group with `perspective` is a 3D context whose planes the core sorts, splits and hits in 3D (D75). There is no depth buffer | 3D effects need one property beyond the matrices. The core draws worlds of planes; dense geometry and complex 3D scenes belong in clients, shown as planes. D75 reopened this decision. |
| D20 | One logical scene; each output shows it through a camera | Pan, zoom and the infinite canvas need no extra mechanism. |
| D21 | The core places popups, subsurfaces and layer surfaces; toplevels wait for a plugin | The protocols define these positions. Smithay implements them. |
| D22 | A transaction completes when all affected clients commit, or after a deadline; transactions on disjoint surfaces do not wait for each other | A resize needs a client round trip. One slow client must not stop the others. |
| D23 | A hardcoded safety layer: Ctrl+Alt+Backspace quits, Ctrl+Alt+Escape resets, Ctrl+Alt+F1 to F12 switch the VT, SIGUSR1 resets while the main loop runs; while the session is locked, only the VT switch and SIGUSR1 work, so nobody at the lock screen quits or resets the session; a watchdog that blames the client whose visible nodes cost the most for slow frames, removes its effects and then disconnects it, and never resets the session (D57); a watchdog thread on a heartbeat of the main loop for a hung loop (D64); a binding that revokes the capabilities of all clients | A recovery path must not depend on a file that an agent can break, or on a main loop that hangs. One client without grants must not take the window manager, the grants and the effects of the others down with it. A quit at the lock screen loses the work of the person who locked it. |
| D24 | The core renders an output only when it has damage; a layer keeps its texture until its subtree changes; a fullscreen surface without effects uses direct scanout | Battery life and GPU load. |
| D25 | No undo history and no plugin state store in the core | A destroyed client cannot come back. The reset and the views in git cover recovery. The scene holds all state. |
| D26 | Xwayland through `xwayland-satellite` | Keeps the core small. |
| D27 | Output configuration through `wlr-output-management` and through `output.configure`, on the same path | kanshi and wlr-randr exist. An agent has no wlr-randr in every session. |
| D64 | A watchdog thread watches a heartbeat that the main loop bumps after each dispatch; the loop wakes at least once a second. After 3 s without a beat, the thread logs the stall with the action that follows. After `CHORA_HANG_ABORT_S` seconds without a beat, 30 by default, it aborts chora with SIGABRT and a core dump, so that the session can start again; 0 means never abort. The stall and the abort lines go to fd 2 with a raw `write(2)`, without the lock of tracing or of `std::io::stderr`. The SIGABRT handler then prints the backtrace of the watchdog thread, not that of the main loop; the core dump has all threads. The watchdog counts only the time that it watched: a look that comes a second or more after the one before means that its own thread did not run, and that time is no stall, up to a ceiling of four abort times of wall time without a beat. The frame watchdog of D57 stays on the main loop | A hung shader or driver blocks the main loop, so the frame watchdog and SIGUSR1 cannot act. Only another thread sees the hang. An abort ends the session, so the user can start it again, and leaves a core dump for the bug. 3 s is above the idle wake-up of 1 s and below the 5 s of the 0.9 gate. A main loop that hangs inside a log write holds the log lock, and the watchdog must not wait for it. A hang of 30 s is longer than any slow frame of llvmpipe, and the user waits no longer than that. A process that was stopped, or starved for longer than the abort time, would otherwise abort at once when it runs again. |
| D68 | Superseded by D75: the space is built without the spike. The portal, output textures and virtual outputs stay planned under D69, D70 and D75 | The owner decided on 2026-11-09 to build robust 3D now, without the measurement. |
| D69 | `output.add` with the flag `virtual` creates a virtual output on every backend, for the main socket only. The client that creates it owns it: the output ends with its creator, after the grace time. The core renders a virtual output only as a texture source, so a window manager on it runs with `--output NAME`. A virtual output is in no list of real outputs: not in the pointer layout, `wlr-output-management`, kanshi or the portal for screen sharing. The emergency reset removes virtual outputs first and puts every window on a real output. At most 16 exist, a side has at most 4096 pixels, and all together hold at most 2^26 pixels | A window on a virtual output that no portal shows is alive but invisible, so the reset must reach it. One owner per output needs no new concept. |
| D70 | A shader node that shows a texture source can carry the property `forward`. The core then passes pointer input that hits the node to what the texture shows, mapped by uv. Only a client with the capability `node.portal` (D33) sets it on a portal onto a real output; into a virtual output of its own, a client forwards without it. The safety layer and the grabs run before the forwarding, and it stops while the session is locked. The portal is the tool for a desktop pane: a portal at 1:1 replaces an `output.present` method, which is not built | Forwarding real input to other clients can click through a transparent portal, so only a trusted client may do it. |
| D82 | The watchdog counts the run queue wait of all threads of the process as host load, not as cost of the scene. A frame that is late because the process waited for a CPU blames no client; the core logs at most once a minute that the host is busy. A costly scene beside idle threads still blames | Under the software renderer the llvmpipe threads do the work and wait for a CPU while the main thread sleeps. Beside 8 busy loops on 4 CPUs at 2560x1600@2 they waited 11.8 s each in 20 s, the main thread 4.3 s, so the slow frames passed as costly and the watchdog dropped the effects of all clients. This refines D57 and D64. Cost: one `schedstat` read per thread and frame. Commit `f67ad247` |

## Plugins and API

| # | Decision | Reason |
|---|----------|--------|
| D28 | Plugins are IPC clients; the core offers `animate` and frame events with the predicted presentation time; in-process WASM plugins come only after a measurement shows the need | Agents work in seconds, not frames. One mechanism, any language, crash isolation by the OS. `tests/ipc-bench.sh` measures a transaction with a mesh of 8x8 cells at 0.17 ms in the median and 3.6 ms at the 99th percentile, nested and with software rendering. |
| D29 | JSON-RPC 2.0 with one message per line on Unix sockets; `hello` negotiates the protocol version and the features; errors carry a stable code and data | Agents and shell scripts reach it without bindings. A versioned protocol lets plugins in other repositories check what they get. |
| D30 | The core starts one startup command with `WAYLAND_DISPLAY` and `CHORA_SOCKET` set | The startup command starts the plugins, or a systemd target. |
| D31 | The owner of a node is a client name; only the owner changes a node; another client requests a change, and the core sends the request to the owner; plugins export methods with a description and a JSON schema | An agent asks the window manager instead of fighting it. |
| D32 | Queries use JSON filters; a query returns all current matches; subscriptions start with a snapshot, and events have sequence numbers | A schema describes the filters. Agents get predictable results and miss no event. |
| D33 | Each client has a socket directory with an IPC socket and a Wayland socket of its own that hides the privileged protocols; the socket fixes its name and its capabilities; `input.inject`, `screen.capture`, `input.grab-any`, `methods.call`, `methods.privileged`, `activation.token`, `node.portal` (D70) and `session.quit` are capabilities | A client cannot take another name or give itself capabilities. A container mounts one directory and needs no configuration. |
| D34 | MCP outside the core: `choractl mcp` over stdio on rmcp, with tools for whole tasks and one tool per exported plugin method | The core stays free of MCP. The official SDK carries the protocol. |
| D35 | The core reads no configuration; `choractl` loads YAML views and `~/.config/chora/clients.yaml`; a flavor is a directory with a systemd target; the configuration holds no secrets | Policy and service management do not belong in the core. |
| D36 | The GitHub organization is `chora-desktop` (`chora` is taken). D77 replaces its plan of one repository per plugin and a packaging repository. The organization and the split come after 1.0; until the split, the core repository holds the core, the plugins and the services, and they build with it | Plugins and services get their own owners and releases once the API of `chora-scene` is frozen at 1.0. The core keeps the definition of the API. |
| D58 | A client changes how a node of another client looks, its opacity, effects or meta, only through the owner: `node.requested` has the action `update` (D31). The window manager applies the change and keeps it across layouts. Clients on a confined client socket can send the request `update`, as `move`. An `update` that mixes owner-only props with opacity, effects or meta fails with an error that names the owner-only props. An `update` for an owner that does not subscribe to `node.requested` fails, because nobody would apply it. A client asks for an animation of a node of another client with the action `animate` of `node.requested`. The owner applies it or refuses it. A function of `chora-kit` passes these requests through for every window manager. Clients on a confined client socket can send `animate`, as `update` | The owner stays the only client that changes its nodes, and an effect plugin works with every window manager. A look that a new layout drops does not hold. |
| D59 | The answer of `scene.apply` carries `warnings` with stable codes, for example for a surface attached under a group with `input: pass`, or for a layer whose subtree (the layer and every layer under it) needs more pixels than the budget of every output; a drop at render time stays the event `layers.dropped` | Some transactions succeed but do not give the result that the client expects. A warning tells the client without a capture. |
| D61 | `choractl mcp` keeps `keep_nodes`; after a restart, an agent removes its own old nodes (#101) | No change in the core or in `choractl`. An agent knows which of its nodes still matter. |
| D62 | Each plugin exports `settings.get` and `settings.set` through the plugin runtime of `chora-kit`, with a schema in `methods.export`. The plugin checks the values, applies them at once and then saves them in its YAML file in `$XDG_CONFIG_HOME/chora/`, for example `chora-tiling.yaml` and `chora-xp.yaml`; a change that cannot be applied is not saved, and a change that cannot be saved stays applied with an error to the caller. The plugin is the only writer of its file. A save renames a new file of mode 0600 over the old one; through a symlink, the save replaces the file that the symlink points to, so the symlink stays. Edits by hand apply with `settings.reload`, which the runtime exports with the other two methods and which reads the file again, or at the next start. `settings.set` takes a JSON merge patch (RFC 7386): structs and maps merge, other values replace, and `null` removes a map entry or resets a setting to its default. A setting that the file leaves out takes its default. A save writes only the settings that differ from the defaults: a changed map whole, and `null` for an option that the user cleared. A file that does not parse or check does not stop the plugin: it starts with the defaults, logs the error and leaves the file as it is, and `settings.set` and every other save refuse until a `settings.reload` succeeds. The file replaces the command-line flags of `chora-xp` except `--theme`, `--config`, `--slow-motion` and `--output`. On a client socket, `settings.set` and `settings.reload` need the capability `methods.privileged` besides `methods.call`, because the settings hold commands that the plugin runs; so does each method that its export marks `"privileged": true`, such as `app.open` and `scene.save` of `chora-mc`, which start programs. `choractl mcp` confines its connection of the main socket with `hello {confined: true}`, so these rules and `activation.token` hold for an MCP agent too until the user grants its name. A generic settings form is not part of 0.8 | One interface serves `choractl`, MCP agents and the dialogs of the plugin. The file keeps the settings. |
| D65 | A client emits its own events with `events.emit {event, data}`. The name is the client name, a dot and a name of the client, for example `voice.state`; the core refuses any other name. A client whose name starts as a namespace of the core events, such as `surface` or `output`, emits nothing. The core sends the event with `client` and `data` to the connections that subscribed to its name or to a pattern `PREFIX.*`, such as `voice.*`. An empty subscription means every core event, not the events of clients. In `events.subscribe`, a name outside the core namespaces is the event of a client; a typo in a core name stays refused. The data has at most 64 KiB. A client name emits at most 32 events per second; the core refuses the rest with code 6 and does not coalesce, so a client sends the last state of a burst again. Any named client may emit, also through a client socket without capabilities, because an event only reaches subscribers. Any connection may subscribe to the events of other clients, by the same rules as core events, also a confined client socket. The voice agent emits `voice.state` (the `agent.set` fields; with `name`, a sub-agent such as `coder`) and `voice.say` (a sentence when its sound starts) and `voice.confirm` (a question with its full command, then its end) on its connection `voice`; `chora-mc` and `chora-xp` subscribe to `voice.*`; `chora-mc` keeps `agent.set` and `hud.say` for other clients. Amended on 2026-11-19 (PM decision, review r1 of `claude/cut2`): the names `look.theme` and `look.view` are the one exception to the name rule of a client. The core stamps `data.look` with the name of the emitting look on them, so that a subscriber, such as the assistant, knows which look spoke; a subscriber trusts `data.look` only on these two names. Open for the next core lane: refuse the client name `look` or stamp every `look.*` event. Merge of `claude/cut2` pending | A HUD needs the state of an agent when it changes, without polling and without a method of the HUD in the agent. The prefix makes the emitter visible: no client fakes a core event or the event of another name. A name of the main socket is still taken by whoever connects first; a client socket fixes it (D33). The limits protect the 8 MiB output buffer of a subscriber. A refusal tells the emitter; a silent drop would not. |
| D71 | A role is a method namespace, for example `horizon.*`. A plugin that needs a role checks at run time with `methods.list` that a client exports the namespace. The start order comes from `Wants=` and `After=` in the systemd target of the flavor. There is no manifest field for dependencies | Any client that exports the namespace fills the role, so plugins stay exchangeable. systemd already orders units. |
| D78 | The core sets `injected` on every input event of a person that `input.inject` could have made: `input.key`, `node.key`, `input.button`, `input.moved`, `pointer.entered`, `pointer.scroll`, `pointer.pressed`, `pointer.moved` and `pointer.released`; `pointer.left` stays without it. A plugin drops these events unless it takes injected input as the person's. Construct, mc, tiling and xp have the setting `test_accept_injected_keys`, `false` by default and for tests only; notify and the assistant have no setting and follow only the environment variable `CHORA_TEST_ACCEPT_INJECTED_KEYS=1`, which turns the switch on for every plugin | A client with the grant `input.inject` could press a binding, click Start, drag a window or walk a camera for the person. Automation calls the methods of the plugin instead, such as `window.give` (D55). The gates set the switch on to drive bindings, and `tests/gate-injected-presses.sh` runs with it off and expects that an injected press does nothing. Cost: every new plugin handler for input must read the flag; `tests/injected-optout.py` and `tests/guards.sh` refuse a binding of the field under another name. Commits `0a3224b`, `4d917c6`, `78d79db`, `622d372`, `0a3d004` |

## Designs

### D55: window managers per claim

Issue #73 calls the area of a window manager a view. The glossary uses
"view" for a YAML arrangement (D5), so this design says **claim**. The
design has two steps. Step 1 is the handover. Step 2 adds claims and the
routing of new toplevels.

#### Step 1: handover

Window manager A hands surface `s1` to window manager B:

1. A owns `s1`, for example at the end of a drag out of its area. A knows
   B by a fixed name or by a `meta` tag on the root group of B.
2. A sends `remove: {id: s1, to: B}`. `to` must name a connected client
   that holds a claim, because only window managers receive windows, and
   a reservation that B does not attach within 5 seconds ends as in
   item 5. As at every `remove`, the surface becomes detached and loses the
   keyboard focus.
3. The core reserves `s1` for B and sends `surface.detached`, which
   carries the surface alone. An `attach` of another client fails.
4. B attaches `s1`, places it by its own rules, and can give it the
   focus. A plugin that adopts every detached surface needs no change.
5. When the last connection of B closes, the reservation ends. With
   `resume`, it ends after the grace time. The core then gives the
   surface back to the window manager that gave it, one level only. Without
   one, it sends `surface.detached` to all, and any client can attach the
   surface. A virtual output of the ended manager ends with it (D69).

**Focus and grabs.** The keyboard focus does not move with the surface.
The receiving window manager sets it with `focus` after the `attach`.
Grabs belong to connections and do not move. A ends its drag at the
release of the button, and then hands the surface over. The client of the
surface keeps its pointer and keyboard input as before.

#### Step 2: claims

A claim is a rectangle in scene coordinates: the property
`claim: [x, y, w, h]` of a node. The owner of the node holds the claim. A
window manager sets it on its root group, and the claim ends with its
node. Window managers claim the whole work area of their outputs. An
output shows a claim through its camera. So two window managers sit on two
outputs, or at two places in the scene, and a camera move switches one
output between them. With claims, A finds B in the claims of
`scene.query`.

At the first commit of a toplevel, the core picks its window manager.
The first choice is the owner of its parent toplevel, so that a dialog
stays with the manager of its window. The next choice is the window manager that
the starter names with an activation token (D42, D72). The last choice is
the owner of the smallest claim that contains the pointer. The focus does
not decide. The core reserves the surface for the named window manager,
as at a handover. Outside of all
claims, any window manager can take the new surface.

Amended on 2026-11-11: the order that the core follows is in
[Window managers](api.md#window-managers). After the parent comes the
window manager that a click of the user chose: a press of a real
pointer button on a point of a claim with no window under it chooses
the owner of the smallest such claim for the next new windows. A person
who clicks the empty screen of another window manager expects the next
window there. The choice ends with the next press of the user elsewhere
and when the keyboard focus changes. An injected press chooses nobody.

**The drop target.** A drag that ends outside the claim of A goes to the
owner of the smallest other claim that holds the drop point; without one
there, the surface stays with A.

**Shared pointer bindings.** Window managers that each hold a claim can
grab the same pointer button binding, but only on the main socket: a
client of a client socket may set a claim for its own windows, and with
a claim a little smaller than an output it would win every press. A
press of a shared binding goes to the grab of the smallest claim under
the pointer, else to the first grab, with its moves and release; key
bindings keep one owner.

**Out of scope for now.**

- The drop position: B places the surface by its own rules.
- A drag that continues in B after the handover.
- An embedded GNOME session in a claim.
- Claims under `screen:NAME`.

## Rejected proposals

| Proposal | Reason |
|----------|--------|
| Versioned docs with mike are too much | The project conventions use mike. |
| Hooks without matching files | The project conventions use this hook set in every repository. |
| Cairo and Pango, or another 2D engine, in the core | The core composites and draws no vector graphics. Text comes from the text node on cosmic-text (D18), shapes from rects and shader nodes. Plugins draw rich chrome themselves, for example with tiny-skia and resvg. |
| An exclusive keyboard grab | Typing must work. Clients that need every key get it through Wayland (D45). |
| A depth buffer in the core | It does not order translucent edges and coplanar layers, and it needs an attachment on the framebuffers of Smithay. The core sorts and splits the planes of a 3D context (D75). Dense geometry belongs in clients (D19). |
| A rewrite from scratch | The scene model, the API and the safety layer hold. The milestones change the rest step by step (D52). |
