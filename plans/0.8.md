# Work plan 0.8 for a local pi agent

This plan is for an unattended pi session on a small model. Do the tasks
in order. Do not invent extra tasks. The scope and the gate of 0.8 are in
`docs/roadmap.md` (section "0.8: Agent read model"); the gate checks are
numbered there.

## Rules (read first, follow always)

- Repo: `~/Projekte/chora`, branch `dev`. Never push. Never rewrite
  history (no amend, no rebase, no reset). Never touch `services/voice/`.
- Cargo is not on PATH: run `micromamba run -n chora cargo ...`.
- Before each commit run, and fix until all pass:
  1. `micromamba run -n chora cargo fmt --all`
  2. `micromamba run -n chora cargo clippy --workspace --all-targets --locked -- -D warnings`
  3. `micromamba run -n chora cargo test --workspace --locked`
- Tests that render need the Mesa EGL variables of CONTRIBUTING.md. Tests
  that failed before your change for lack of a GPU may stay red; compare
  with a run on the commit before your change.
- Commits: conventional, imperative, at most 68 characters in the subject.
  Stage files by name. No AI attribution lines.
- One task = code + a test that fails without the change + the docs in
  `docs/api.md` (sections Selectors, Events, Input injection, Plugin
  methods, MCP tools) or `docs/architecture.md`. Docs: at most 25 words
  per sentence, active voice, no em or en dashes.
- If a task needs more than about 300 changed lines, or you are not sure
  what the right behaviour is: stop that task, write `status: open (ask
  Marcel)` with your question in `plans/0.8-state.md`, and go to the next
  task.

## Session mechanics

Follow `~/.agents/skills/local-pi-session/SKILL.md` and its
`reference.md`:

- One driver script loops over the tasks below, one at a time.
- A heartbeat restarts the driver if it dies; there is no cron here.
- At most 2 pi sub-agents at the same time, each with a session, each
  under `timeout 3600`. Reviewer prompts ignore `target/` and
  `services/voice/`.
- State lives in `plans/0.8-state.md`, one line per task:
  `T<n>: todo | doing | review | done <sha> | open (<reason>)`.
- For each task: implement sub-agent commits; review sub-agent reads
  `git show <sha>` read-only and ends with `open: <n>`; audit the session;
  fix round on findings; after 3 rounds without zero findings mark the
  task `open`.
- When all tasks are `done` or `open`, write `plans/0.8-done.md` and
  stop the heartbeat.

## Tasks

### T1: JSON filters in queries (D32)

- Goal: `scene.query` accepts a JSON filter next to the selector string:
  at least `owner`, `kind`, `app_id`, `focused: true`, `visible: true`
  and `output: "NAME"`. All fields must match; an empty filter matches
  everything.
- Look at: `fn query` in `crates/chora/src/ipc.rs`, the selector parser
  in `crates/chora-scene`, the `rects` of T2 from 0.7 for `visible`.
- Test: unit tests in `ipc.rs` for each field and for a combined filter.
- Docs: the filter fields under `## Selectors` in `docs/api.md`.

### T2: snapshots and sequence numbers in subscriptions (D32)

- Goal: `events.subscribe` answers with a snapshot of the current scene
  (a normal query result) before the first event, and every event after
  it carries `"seq": <u64>` that rises by one per event per connection.
- Look at: the event dispatch in `crates/chora/src/ipc.rs` (the same
  place that writes `events.dropped`), `events.subscribe`.
- Test: gate check 5 as a unit test: subscribe while a transaction runs,
  apply 1000 small transactions, assert every sequence number once, in
  order, with no gap.
- Docs: under `## Events`: the snapshot, `seq`, and how a client uses
  `seq` after a reconnect.

### T3: inject a node and a point

- Goal: `input.inject` accepts `{"node": ID, "point": [x, y]}` for
  clicks and moves: the node id plus a point inside the node, in node
  coordinates. The core turns it into screen coordinates through
  `rects` (0.7 T2), so pan and zoom need no client math.
- Look at: `crates/chora/src/inject.rs` (the `input.inject` handling),
  the rect map of a query.
- Test: a node under a scaled parent: the injected point lands where the
  query says, in process. Gate check 2 comes with `choractl mcp` (T6).
- Docs: under `## Input injection`.

### T4: change requests for nodes of other owners (D31)

- Goal: a client that does not own a node can `focus`, `move`, `resize`
  or `close` it only by request: the core delivers
  `node.requested {node, client, action, args}` to the owner; the owner
  decides by doing it or not. `chora-tiling` answers focus, move and
  close for its windows; unhandled actions stay unanswered.
- Look at: the write path in `scene.rs` (the refused-not-owned error),
  the `surface.requested` event chora-tiling already subscribes to, and
  the tiling methods of 0.7 T10.
- Test: unit test: client B requests a close of A's window, the owner
  gets the event; tiling applies a requested focus (battle workflow W1
  drives it).
- Docs: under `## Window managers` or `## Events`, naming D31.

### T5: described methods with JSON schemas

- Goal: `methods.export` takes `{name, description, input_schema}` per
  method (old plain names still accepted), and a new `methods.list`
  answers what is exported with description and schema.
- Look at: `methods.export` in `crates/chora/src/ipc.rs`, the export
  calls in `plugins/chora-tiling/src/main.rs` and in chora-xp.
- Test: export with a schema, list it back; a schema-less export still
  works. Give the tiling methods their descriptions and schemas.
- Docs: under `## Plugin methods`.

### T6: `choractl mcp` on rmcp

- Goal: rewrite `crates/choractl/src/mcp.rs` on the rmcp crate (add the
  dependency): stdio MCP server, one tool per exported plugin method
  (from T5), the built-in tools `query` (T1 filter), `wait` for a
  selector or filter, and `wait_events` for the next matching event
  (T2). Requests run in parallel; a cancelled call ends within 100 ms.
- Look at: the existing hand-rolled `mcp.rs`, T1-T3 for the primitives.
- Test: gate check 1 and 3 as far as a stdio test can go: a JSONRPC
  line-per-line script that lists the tools, calls a tiling focus, and
  cancels a waiting `wait_events`.
- Docs: rewrite `## MCP tools` to the real tool list.

### T7: text injection types every character

- Goal: `input.inject` with `text` types every character through the
  Wayland text input path (keysyms and `zwp_text_input_v3` preedit or
  commit), also characters the current keymap cannot reach, for example
  German umlauts on a US layout.
- Look at: the keymap and keyboard code in `crates/chora/src/input.rs`
  and the `text` handling in `crates/chora/src/inject.rs`.
- Test: in-process: a client with a US keymap receives the commit
  `Grüße äöüß` unchanged (gate check 4; a foot-based check stays manual).
- Docs: the `text` paragraph under `## Input injection`.

### T8: injection indicator and agent revoke binding (D23)

- Goal: while a client injects input, a visible mark shows it: the core
  puts a small rect of its own next to the pointer or over the focused
  surface, and removes it 500 ms after the last injected event. A new
  safety-layer binding (fixed, like Ctrl+Alt+Backspace) revokes the
  capabilities of all clients that hold only agent capabilities.
- Look at: the safety layer in `docs/architecture.md`, the injected
  input path, node creation inside the core (the reset grid does it).
- Test: gate check 8 as a unit test (the revoke binding); gate check 7
  (indicator on a capture) as a headless session test.
- Docs: the safety layer section in `docs/architecture.md`.

### T9: the text node (D18)

- Goal: node kind `text`: a string, a font family, a size, a color and a
  maximum width; cosmic-text shapes it, finds fallback fonts, and the
  headless renderer draws it. Props update like a rect's.
- This is the largest task: if it passes 300 changed lines, stop and
  write `status: open (ask Marcel)` with your split proposal.
- Look at: the node kinds in `crates/chora-scene`, the glyph handling of
  surfaces (title text), `docs/dependencies.md` for cosmic-text.
- Test: gate check 9: a text node shows `Grüße 你好 🙂`, a pixel test
  against a reference capture.
- Docs: the `text` row in the node kinds table of `docs/api.md`.

### T10: the watchdog under two stress clients

- Goal: decide and implement how the watchdog blames clients when
  several owners make frames slow at once. The battle finding: snake is
  disconnected while the budget probe churns nodes. Options: blame the
  owner with the largest cost share only when its share is above half,
  otherwise blame none and only drop effects; or a tunable budget per
  owner. Choose one, keep it simple, write the reasoning into
  `docs/decisions.md` as a new D.
- Look at: `crates/chora/src/safety.rs` (the blame logic, the per-client
  pause of `54ccba5`), `Scene::load_by_owner`, the W5 workflow.
- Test: unit: two owners with loads 3000 and 2500 - no disconnect of
  either below the rule you picked; the W5 workflow stays honest.
- Docs: the watchdog paragraph of `docs/api.md` and the new D row.

### T11: the silent core death, forensics with last words

- Goal: run the battle W5 workflow until the "core dead" finding
  appears (or 10 iterations pass). Since `5b41d48` a faulting signal
  logs a backtrace, and `4444484` records State, VmRSS and wchan inside
  the finding. Classify the death: backtrace - file the bug it shows;
  `no-process` without a backtrace - an external SIGKILL, write it into
  `tests/battle/FRICTION.md` as environmental and close the finding;
  a State with a wchan - a hang, open a core issue with the facts.
- Look at: `tests/battle/FRICTION.md` (0.7 backlog), the finding text.
- Test: the classification itself is the deliverable; findings.md
  changes status to `fixed in <sha>`, `harness: <file>` or
  `deferred: <plan>`.

### T12: gate checks of 0.8

- Goal: walk the gate list of roadmap section 0.8 end to end. Run what
  runs headless (checks 1 to 10 with `tests/headless-session.sh` and a
  stdio MCP client), script each check as
  `tests/gate-0.8-<n>.sh`, and write the results into
  `plans/0.8-gate.md`. A check that cannot run here says why.
- Test: the scripts are the tests; keep them idempotent.
- Docs: none.

## When the loop is done

Write `plans/0.8-done.md`, one line per task with its commits, then run
the battle suite once to `THE END`, and leave a report like
`plans/0.7-report.md`. Pushing, tagging and releases stay with Marcel.
