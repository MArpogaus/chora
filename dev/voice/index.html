    chora-voice: the voice agent in Rust (draft specification)¶

    Status: draft, 2026-10-30. WP0 to WP8 are done. Sources: the Python agent of before WP6 (services/voice/agent.py in git history), D53, D58, D61, D62, docs/api.md, the chora-kit runtime and settings, choractl mcp, and live probes of the Gufo servers.

    chora-voice is the voice agent of chora. It completed full voice turns against the live servers in WP6; the Python agent and voice-agent.service are gone, and chora-voice.service runs it (services/voice/README.md).

    1. Goals and non-goals¶

    Goals:

    • One binary chora-voice in the crate services/voice: a chora client on the chora-kit runtime, with D62 settings.
    • Silero VAD on tract (pure Rust, no C library) as the speech gate.
    • Always listening, with the local words "Schlaf" and "Hör zu", plus the push-to-talk (PTT) key. The wake word goes through the ASR.
    • A cancel word stops the current turn at any time, also while the agent speaks or works.
    • Spoken yes/no confirmation before the tools of a configurable list.
    • Separate mute switches for the mic and the speaker.
    • No silent failure; a latency per stage for each turn; a state for the HUD.
    • Replay tests that measure speech detection and barge-in against labelled recordings.

    Non-goals: new ASR, TTS or LLM servers; a keyword-spotting model; an own echo canceller (the PipeWire one stays); a GUI; a package before the agent completes full turns.

    2. Architecture¶

    One process. The core is one thread that reads one input channel. All other actors send their inputs into that channel, and the core sends effects back to them. The core holds the state machine as a pure function step(state, input) -> (state, effects), so unit tests need no IO. WP4 adds a tokio runtime for the network actors; they send into the same channel.

    Actor Job
    audio_in A thread: the capture command at 24 kHz mono, 32 ms frames (768 samples), Silero probability and RMS per frame
    audio_out The playback command at 24 kHz for TTS and earcons; knows when the written sound ends; stops at once
    asr One websocket per utterance to Qwen3-ASR realtime, PCM in 1 s pieces
    tts One websocket per sentence to Qwen3-TTS, one sentence ahead
    llm /chat/completions with SSE and tools
    tools MCP client of choractl --name voice mcp, the coder tools, read, the confirmation gate
    coder One background coding task, as in Python
    chora A thread with the chora-kit runtime: methods, settings, PTT grab
    hud A thread: times the events of the HUD for the chora thread; the indicator node on its own connection NAME-hud (WP8)
    core State machine, speech gate, history, word matcher, turn metrics

    Audio: the ASR takes 24 kHz only (WP0), and the TTS sends 24 kHz. So the mic records at 24 kHz, and the ASR gets that PCM unchanged. Only the VAD gets a 16 kHz copy: a 33-tap windowed-sinc low-pass at 7 kHz, then two samples out of each three. Subprocesses replace the pipewire crate, which needs bindgen and C headers. The commands are settings, so arecord/aplay are a fallback without code. Tests feed WAV files.

    Tool layer: LLM tools go through MCP (rmcp client). The tool schemas and the plugin tools stay in one place, and chora_mcp can still run tools in a container. The agent's own needs (PTT grab, methods, settings, indicator) go through the runtime connection. This replaces the PTT polling through wait_events.

    The chora thread runs runtime::run and runtime::serve of chora-kit; runtime::dispatch is public already. Methods send an input with a reply channel to the core and wait up to 1 s for the new state. When the runtime gives up after 30 s without chora, the agent exits with 1.

    3. State machine¶

    State Meaning
    sleeping Hears only wake words; PTT records a request
    listening Waits for speech
    recording Collects an utterance
    transcribing Waits for the ASR
    thinking Waits for the LLM, no sound
    tool A tool call runs
    confirming Waits for yes or no
    speaking Plays the reply
    working Listening while a coding task runs

    The agent starts in listening (awake). The core derives the state from what goes on, in this order: an utterance in progress is recording; an utterance whose text waits is transcribing (not while asleep); a reply is confirming while a question waits, speaking while its sound plays or ran dry less than 1.5 s ago (0.25 s after a question that waits for its answer, so that the speech gate hears a short "Ja"), else thinking or tool; else listening or sleeping. So speech during a reply shows as recording and transcribing, and the state of the reply comes back after it.

    From Input To
    sleeping Short utterance with a wake word listening, earcon
    sleeping PTT down recording, then back to sleeping
    listening, working VAD onset or PTT down recording
    recording silence_ms quiet, PTT up, or max_turn_ms transcribing
    recording Less than min_speech_ms speech previous state
    transcribing Sleep word sleeping, earcon
    transcribing Cancel word, empty text or echo previous state
    transcribing Code cancel word previous state; the coding task stops
    transcribing Other text thinking
    thinking First sentence speaking; tools run in parallel
    thinking Tool call on the confirm list confirming
    thinking Other tool call tool
    tool Result or timeout thinking
    confirming Yes tool
    confirming No, two unclear answers, a new request, or timeout thinking; the result says which
    speaking Audio and LLM done listening or working
    busy states Cancel word, voice.cancel, PTT down listening, earcon
    any Sleep word or voice.sleep sleeping, earcon
    sleeping voice.wake listening, earcon

    An ASR error sounds the error earcon. The final text of an older utterance still counts; a late interim text drops. An utterance while asleep only looks for a wake word; one by the PTT key is a request, and the agent sleeps again after the reply.

    Barge-in while speaking: speech over the barge-in gate (section 4) for barge_in_ms pauses playback at once. The unplayed sentences stay queued. A cancel word drops them and cancels the turn. Empty text or echo plays them from the cut sentence; a spoken yes or no to a question skips the cut question. Other text ends the reply; the history keeps only the played text, and the new text starts a reply. The utterance of a barge-in starts with the barge-in speech and preroll_ms before it, and ends as any other after silence_ms of quiet, so a short pause makes no second turn. Text that is not echo ends the reply the same way while its sound plays, also when it came without a barge-in.

    Each heard text that is not a command word shows first in the HUD, as phrases.heard ("Heard: ...") through the say event.

    Speech while thinking, tool or confirming: each utterance goes to the ASR at once. A cancel word cancels. In confirming, the text is the answer, but only speech that starts after the question starts to play. Other text goes into the next LLM round of the running reply, as a user message (Inject; the chat reports it back as Heard). This also holds after the answer of a round: when new words came while the LLM answered, one more round hears them. After the last round of tool_rounds, new words get tool_rounds more rounds in the same turn; they do not wait until the reply is said. Short text goes in too ("Und größer.", "Nein, rot."). Only a pure yes or no waits in the queue. It never answers a question. A call that would ask does not ask while new words wait: it does not run, and its result is "Not confirmed: the user said something new; nothing happened". Texts that no round heard start the next reply together, as one message (queued in the state record). No speech is dropped.

    A turn whose first round calls tools without words says phrases.ack ("One moment.") once. An answer whose last sentence announces an action in the first person, but calls no tool, gets one more round per turn with a note to call it or to say that it will not. A turn that already ran a tool gets no such round. Only explicit forms announce: "let me ...", or "I'll", "I will" or "I'm going to" before a verb of action. In German, these are "ich werde ...", "lass mich ..." and "ich schaue nach", "mal" or "kurz". These are no announcement: a question, "let me know", "I'll be here", a negation ("I will not", "nicht", "kein"), and other German "ich" sentences ("Ich helfe dir gern.", "Ich starte den Loader.").

    An answer that ends with stop, calls no tool, and whose words do not end with ., !, ? or … (also before a closing quote) is cut: Gufo 0.27 ended rounds after 1-12 tokens ("I’m setting the", "I’ll send Alt", 2026-10-31). Its last words after the last spoken sentence never play and never go into the history. One more round runs with the note "[Your last answer stopped mid-sentence. Answer again in full.]" at the end of the request; the note does not go into the history, because the same request gave the same fragment again. That round does not say again the sentences that already played, and a cut round does not count toward tool_rounds. After two cut rounds in a row, the emergency brake drops the history before the last words of the user, and one more round runs. A third cut says phrases.lost ("I lost the thread, please say it again.") and ends the turn. The cut check comes before the announcement check, and a cut answer never gets the announcement round.

    Cancel stops only the current turn: the reply task drops the SSE request and the MCP call in flight (rmcp sends notifications/cancelled), the history gets the words that played, cut back to the last whole sentence (else without the last word, which may be cut), and a note: for a call in flight "cancelled by the user; result unknown" as its tool result, else chat::STOPPED as a message of the user of its own. The LLM copied a note at the end of its own answer into the next answer, and it copied answers that end mid-word. The agent never speaks or keeps these notes: they go from the stream of the LLM and from the stored answer. Playback stops. A cancel word does not stop a coding task. A code cancel word ("Coding-Aufgabe abbrechen") stops it. Coding results wait for listening or working, and also go into the history.

    Mute: voice.mute has two separate switches. A muted mic starts no turn by VAD, and no barge-in; PTT still records, because the key is an explicit request. A muted speaker plays no TTS and no earcons; the reply text still goes to last_reply and to the HUD.

    4. Speech gate, echo, word matcher¶

    Onset: probability over vad_threshold for onset_ms. End: under vad_release for silence_ms. An utterance keeps at most preroll_ms before the first frame of its onset. The PTT key starts an utterance at once; while the key is down, each frame counts as speech, and only the release ends the utterance.

    Echo (decided in WP6, open question 4): the echo level is the level of the played sound times a coupling. The played level is the loudest RMS of the played frames in the last 160 ms (the sound reaches the mic a little later than it is written). The coupling starts at barge_in_coupling (0.1: the PipeWire echo canceller is assumed) and is learned during playback: a median tracker of mic RMS over played level (steps of 5 % per frame; only 1 % up on a frame that counts as speech). Barge-in needs probability over barge_in_vad_threshold and RMS over max(floor, echo level × barge_in_echo_ratio) for barge_in_ms. The floor is barge_in_min_rms when it is above 0; else it adapts: 40 % of the median of the last five turns' median frame RMS, at least 5, and 15 before the first turn. The learned coupling goes down to 0.00001: the PipeWire echo canceller left an echo of RMS 0.1 under played sound of RMS 4000, and the user's speech had an RMS of 20-70 (live test 2026-10-31). Silero hears such quiet speech late or not at all, so the VAD (not the gate or the ASR) gets the mic with a gain that lifts its recent peak level to 1000: at most 33×, the peak halves in about 30 s. Its utterance keeps that speech and preroll_ms before it: with 100 ms, the ASR heard "verbrechen" for "Abbrechen" (WP6 live). Each utterance, the pre-roll included, goes to the ASR scaled so that its peak is at -3 dBFS: at most 40 dB, never down, without clipping. In the live test of 2026-10-31 the utterances had a peak of 4-63 (RMS 1-8) behind the echo canceller. pipewire/echo-cancel.conf turns on the digital gain control of WebRTC and turns off its noise suppression, the likely cause of the digital zero between the words (not yet verified on PipeWire). A transcript whose words match more than 80 % of the words spoken in the last 3 s is echo.

    Word matcher (no LLM):

    1. Only utterances with up to word_max_ms of speech and four words count. The speech is the VAD frames, without preroll_ms and the end wait: "Schlaf jetzt." had 1856 ms of speech in an utterance of 2848 ms and went to the LLM with the old limit on the length (live 2026-10-31). A command word acts at once, also while a reply thinks, runs tools or speaks.
    2. Normalize: lowercase, no punctuation, ä→ae, ö→oe, ü→ue, ß→ss.
    3. Remove filler_words.
    4. The rest must equal a phrase. Words of four letters or more may differ by one edit; words written together also match ("Codingaufgabe").
    5. Order: code cancel, cancel, sleep, wake, yes, no. Yes and no count only in confirming, by the answer rules of section 5 and without the limits of rule 1.

    While asleep, each short utterance goes to the ASR to find a wake word. A keyword-spotting model can replace this later.

    5. Confirmation¶

    A rule matches by tool (glob), and optionally by the command kinds of apply_commands, by argv0 of run_program, or by method (glob) of call_method. The agent speaks the prompt of the rule, with the program of run_program in place of {program}, the argument NAME in place of {NAME} (a missing one stays as it is) and all text, number and boolean arguments in place of {args} ("Shall I change the screen to output winit, scale 1.5?"), and waits for yes or no. The method confirm answers from a key or the HUD (WP5; privileged, so a confined client needs methods.privileged), the spoken yes and no since WP6. Only speech that starts after the question starts to play is an answer. A queued text never answers. Without speaker sound, the question counts from when it is asked. Only a pure yes or no answers: one or two yes phrases, or one or two no phrases, and filler words. Examples are "Ja, bitte.", "Ja, mach das." and "Nein, lieber nicht." A text of fillers only, such as "Bitte.", counts with them. Other text of at most two words is unclear ("1.5", "Ja, nein"). Two unclear answers are a no. A longer text is a new request, also with a yes word in it ("Mach das andere Fenster zu."). A new request is a no, and the text starts the next turn. No answer within confirm_timeout_ms from the end of the sound of the question is a no (a question that is never said waits 30 s longer). The LLM gets the reason as the result: "The user declined the spoken confirmation", "The user did not answer the spoken confirmation in time (15 s)" or "The answer to the spoken confirmation was not understood", each with "; nothing happened".

    A yes with an always_words phrase ("Ja, immer.", "Always.") allows the same action until the agent restarts or takes settings: each settings.set, each settings.reload and each new connection to chora ends all of them, so a stricter confirm applies at once. Then the agent says phrases.allowed ("Allowed for this session."). The same action is the same full argv of run_program, or the same method CLIENT.METHOD with the same parameters (as canonical JSON, keys sorted). For every other call, an always word is a single yes: inject_input, apply_commands, code_task, agent_start, configure_output, the other built-in tools, each settings.set and settings.reload, and each change of the agent's own settings. A question of a sub-agent takes an always word as a yes.

    Two settings list the actions that never ask. allow_programs lists bare program names, such as foot. An entry matches only an argv[0] that is exactly this name, so /home/u/proj/foot asks. allow_methods lists methods CLIENT.METHOD, such as mc.scene.show, matched exactly. At load, the agent refuses an empty entry, an entry with a space, a glob (*, ?, [), a program with a /, and a method without a .. So *.settings.set cannot go in. Neither list applies to the agent's own settings, which always ask.

    Each question also goes out as the event voice.confirm {prompt, detail, id}; id is a text, such as "3". A question about a security key also has physical: true and keys: {yes, no}. detail is the full command or value, never cut: the settings keys and values, the program and its arguments, or the method and its parameters. Every subscriber of voice.* gets it, so secrets are hidden as in the journal: the value of each *_headers key, of authorization, of a key that ends in token, and of a key with api_key, secret or password shows as (hidden). A question of a sub-agent has its prompt as detail. When the question gets its answer, ends or times out, the agent emits voice.confirm {id, done: true}. chora-mc shows the question as a notification, chora-xp as a balloon. The agent cannot see the subscribers of an event. So, while no plugin claims the indicator (section 10), the agent shows the prompt and detail itself: a text node voice-question at the top left of the first output, on NAME-hud. A text node holds 4 KiB, so a longer detail shows only its start there; the event has all of it. Over the rate limit, the last voice.confirm goes again after 1 s.

    While a claimer of the indicator (section 10) is connected, the event also has buttons: true. A HUD can then show Yes and No buttons. A click calls voice.confirm.answer {id, yes} with the id of the event. Only a client that holds indicator.claim may call it, and only for the question that is open now. An old or wrong id is refused. A click is a physical act, as a key press is. So a button also answers a question about a security key. The LLM never reaches the method: it calls no method of NAME (see "Own settings").

    The rule of apply_commands with remove asks only when a target is not a node of the agent's own client (NAME-mcp), or has a node of another client under it; the agent reads the owners and parents with query_scene, and any doubt asks. close always asks.

    Own settings: the LLM may call settings.get, settings.set and settings.reload of the agent's own client NAME, also when skipped_tools hides NAME; no other method of NAME, NAME-hud or NAME-mcp. The tool of its own settings.set takes {"patch": ...} without the schema of the settings, which is about 14 KB and made the LLM narrate; the agent hands the patch on and the client checks it. Each settings.set asks with its keys and values (phrases.settings_set, "Shall I set barge in min rms to 15?"). A security key asks with phrases.settings_security ("Security setting! Shall I set llm url? The full value is on the screen. Press Alt+y for yes or Alt+n for no."). The security keys are allow_programs, allow_methods, confirm, confirm_keys, agent_projects, yes_words, always_words, no_words, phrases, record_dir, sandbox_cmd, unsandboxed, agent_cmd, coder_cmd, chora_mcp, capture_cmd, playback_cmd, skipped_tools, system_prompt, prompt_file, context_docs, indicator, earcons, confirm_timeout_ms, ptt_key, wake_words, sleep_words, each *_url, *_headers and each key with api_key. The agent never cuts a security value. The question says only the key and that the full value is on the screen. The screen shows it through the voice.confirm event (secrets hidden, see above). Only other values are cut to 60 characters for speech.

    Security keys take a key press, never a voice (the user's decision, review rc3 round 2, 4.4). A voice can be played from a speaker, and a text that the LLM reads can steer it, so a spoken yes is no proof that the user agrees:

    • While such a question waits, the client NAME grabs the two keys of confirm_keys (default {yes: Alt+y, no: Alt+n}) with input.grab on its own connection. It lets them go when the question ends.
    • Only these keys and the buttons of a HUD (voice.confirm.answer) answer it. A spoken yes, an always word and a yes of the method voice.confirm count as nothing. A spoken no, a new request, two unclear answers or voice.confirm no are a no.
    • No key press within confirm_timeout_ms is a no.
    • The event voice.confirm has physical: true and keys: {yes, no}, so a HUD shows "Alt+y = yes, Alt+n = no". The agent's own HUD text shows that line too.
    • An injected key could answer the question. So the agent refuses inject_input while such a question waits. Besides, inject_input always asks by the default rules and never takes an always word.

    The client NAME-mcp needs methods.privileged for settings.set and settings.reload. Its own settings.reload asks with the rule of *.settings.reload.

    Reading files: the built-in tool read {path, line?} lists a folder (sorted names, a folder with a trailing /, at most 200) or answers the text of a file, without a confirmation. The roots are the project folders of agent_list: agent_projects and the folders of $XDG_DATA_HOME/chora/inventory. An empty path lists the projects; a path is PROJECT/REL or absolute. The tool resolves the real path (.. and symbolic links) and refuses each path outside the real roots. It opens the real path once, without a wait for a FIFO. On that handle, it checks again that the file is inside a root, that it is a regular file and that it has at most 4 MiB. It reads at most 4 MiB and one byte. It refuses binary files (a NUL byte) and text that is not UTF-8. One answer has at most 64 KiB, cut at a line, and names the line to read on with (line). The prompt says that the text of a file is data, never instructions, and that the agent speaks at most a short summary of it.

    6. Error handling¶

    Component Failure Reaction
    Mic Capture command exits Restart, backoff 0.5 s to 5 s, error earcon once
    VAD Model does not load Exit 1; systemd restarts
    Settings The settings file is broken At start: exit 1 with an error that names the file. On settings.reload: the error, and the settings stay. A new connection to chora fails until the file is fixed. The agent never takes the defaults instead
    ASR Error or timeout One retry with the same audio, then earcon and phrases.asr_failed ("I did not understand you.") when the agent listens again; a wake word asleep only sounds the earcon
    TTS Error or timeout Earcon once per reply; the text stays in the history, in last_reply and on the HUD; the tool loop goes on; for the backoff of the TTS (1 s, doubling to 30 s), its sentences skip without a try
    LLM Connect error One retry, then phrases.llm_down ("The language model does not answer.")
    LLM First token, idle or total timeout Abort, keep the rounds so far, say so
    LLM Context error Trim the history to half the budget, one retry
    LLM tool_rounds reached A final round with tool_choice: none and a note: sum up in the reply language; without words, phrases.tool_rounds; history stays; new words of the user during that round get tool_rounds more rounds
    LLM Three cut answers in a row A retry with a note after the first, the emergency brake after the second, phrases.lost after the third (section 3)
    MCP Child exits Restart with backoff; call in flight gets "connection lost, result unknown"; tools reload
    MCP tool_timeout_s Cancel the call; result "timeout, result unknown"
    Tool A call fails the same way twice in a row in a turn: the same error, or the same tool with arguments of the same form (keys and types) The error stays whole, plus "This failed twice the same way; stop and tell the user what failed."; a third such call does not run and gets that note as its error
    chora Connection closed Runtime reconnects and grabs PTT again; after 30 s, exit 1
    Any thread Panic or end Exit 1; the unit has Restart=always

    The history commits per LLM round; an audio failure never rolls it back. voice.health and the health of the state record show asr, tts, llm, mcp and chora as ok, down or unknown (before the first report), with the last error and its Unix time error_at. Each actor reports its successes and failures. At start, the agent warms the LLM cache, again with the backoff of the LLM until it answers, so the cache is warm when the LLM comes back. Then it says phrases.ready ("Ready.") once, also on the HUD, when it listens; empty turns it off. A failed warm-up says nothing new. A probe connects to the websockets of the ASR and the TTS, without a request, at start, after a new URL, every 30 s, and at the end of the backoff of a server that is down. Earcons are synthesized tones: wake, sleep, cancel, error.

    7. History and token budget¶

    • context_tokens from the setting, else from the server (context_length in /v1/models; Gufo has 128000), else 32768.
    • Budget: context_tokens minus reply_reserve_tokens. The estimate counts the characters of the prompt, the tools and the messages (a picture counts as 4000), divided by the characters per token of the last request: its length over its usage.prompt_tokens (3.0 at the start; requests with a picture teach nothing). No tokenizer.
    • history_tokens (default 12000) bounds the messages after the system prompt, estimated as characters / 4; 0 keeps only the context budget. A long session (dump 2026-10-31: 221 messages, 33k tokens, full of cut answers) made the LLM copy its old answers.
    • Before each request, drop the oldest whole turns until the estimate fits the budget and history_tokens; the last turn stays. A turn starts at a user message, so a tool call and its results go together. Before a new turn, old tool texts shrink to old_tool_chars and lose their pictures, and long arguments of old calls become {"shortened": true}; the last put_asset of each name stays whole.
    • The requests of the last saved_requests turns go to $XDG_STATE_HOME/chora/voice-history.json (default ~/.local/state), in the format of the Python agent (a list of user messages). At start, they go into the system prompt as quoted lines under "Earlier requests of the user", not as chat messages.
    • The system prompt: system_prompt, or the built-in prompt (src/prompt.md, from the Python agent); then the context_docs (FILE or FILE#HEADING for one ## HEADING section), or the built-in ones: README.md, docs/glossary.md and ten sections of docs/api.md, compiled into the binary; then prompt_file. A missing document or heading is an error at start.

    8. ASR and TTS protocol (live probe, 2026-10-30)¶

    ASR (/v1/realtime?intent=transcription, turn_detection: null):

    • The server takes only mono PCM16 at 24000 Hz. At 16000 Hz it answers invalid_audio_event: "realtime input requires mono PCM16 at 24000 Hz".
    • It sends conversation.item.input_audio_transcription.delta events only after input_audio_buffer.commit, all within about 0.4 s, then ...completed. A 3 s sentence took 0.44 s to 0.57 s after the commit.
    • So text while the user speaks needs a new transcription of the growing buffer. The setting asr_interim_ms sets the interval; 0 turns it off.

    TTS (/v1/audio/speech/stream, voice aiden):

    • Per sentence: audio.start with sentence_index, sentence_text, format and sample_rate (24000), then binary PCM, then audio.done. session.done ends the session.
    • The server does not split a text: "Eins. Zwei." and a text of three sentences each came as one audio.start with sentence_index 0 (WP4 live check). So the agent splits the reply into sentences itself, one socket per sentence, as section 2 plans.
    • audio.start gives the text and the start of its sound. The HUD typewriter spreads the words of sentence_text over the PCM length of the sentence.

    9. Settings (D62)¶

    File $XDG_CONFIG_HOME/chora/chora-voice.yaml. A missing key takes its default, so an empty file is valid. settings.set applies at once (a new capture_cmd restarts capture, a new ptt_key grabs again; WP5: a new prompt warms the cache). Edits by hand apply on voice.settings.reload. The client name is the flag --name (default voice). chora-voice --print-config prints all defaults.

    Method of voice Parameters Result
    state none the state record below
    cancel, sleep, wake none the new state record
    mute (privileged) mic: bool, speaker: bool, each optional the new state record
    indicator.claim (privileged) none {}; hides the dot while the caller is connected

    mute, talk, indicator.claim and confirm.answer are privileged: with them, a client could unmute the mic, record, or hide the dot, so that the agent listens without a sign. A client socket needs methods.privileged for them. The export flag cannot depend on mic, so muting needs it too. The plugins chora-mc, chora-xp and chora-construct connect to the main socket, which may call privileged methods.

    The state record: state, since_ms (time in the state), seq (one more per change), awake, muted: {mic, speaker}, turn, last_transcript, last_reply, queued (texts that wait), coder (the parameters of agent.set for the coder, or null before the first task), agents (the parameters of agent.set of each ACP agent) and health (section 6).

    HUD: the agent emits client events (D65) on its connection voice, so a HUD subscribes to voice.* and needs no polling. Only the client named voice emits them; under another --name, the agent emits none. The subscription voice.* also matches a client such as voice.evil, so a subscriber must check that the client of each event is exactly voice. The method state stays for a full state record. The indicator node signals without a HUD: with indicator, a dot of 12 pixels in a corner of the first output, under screen:OUTPUT, in the color of the state (input pass). offset is its distance from the corner. The hud thread places it once per connection, and again when indicator changes.

    A plugin that shows the state itself hides the dot with the method indicator.claim {} of the client voice. The agent records the client name of the caller. The dot hides while one claimer or more is connected. On client.disconnected of a claimer, the agent drops its claim. When no claimer is left, the dot comes back. indicator: false turns the dot off for good. The claims do not survive a restart of the agent. So a plugin claims again on client.connected with the name voice, or when it gets its first voice.* event.

    The events (D65): voice.state {state, task, said} on each change (state mapped to the states of mc: asleep, listening, thinking, working, question, speaking; task the request, said the last reply), and voice.say {state: speaking, text, duration_ms} for each sentence when its sound starts, with the length of its PCM (a late sentence gets the rest of its length). The data are the parameters of mc agent.set and mc hud.say, and chora-mc subscribes to voice.*. A coding task is a sub-agent: voice.state {name: coder, state, task, said} with state working, then done or blocked (failed or cancelled), task the task, and said its last step, then its result. An ACP agent (section 18) is a sub-agent too: voice.state {name, state, task, said, voice, plan, question, log}, and voice.remove {name} when it stops. The hud thread waits for the sound of a sentence and hands the events to the chora thread, which emits them on the connection of the methods: only that connection has the name voice. The chora thread looks for them every 50 ms between the events of chora. Over the rate limit of the core (D65), the last state or remove of each name waits 1 s and goes again, with the states that come meanwhile; a refused say is gone. Another refused event logs at debug level.

    11. Logging and latency¶

    tracing with timestamps to stderr (journald), without colors when stderr is no terminal. RUST_LOG filters; the default is info,tract_linalg=warn. The lines are plain text in the form key=value: one call site per level in log.rs keeps the tracing macros out of the other functions, because clippy counts their expansion into the cognitive complexity. With CHORA_VOICE_LLM_DUMP=FILE the agent appends each LLM request body and the raw lines of its stream to FILE (mode 0600), to see what the server got and sent. Each stage logs start and end with the turn number. A tool call logs its arguments and the start of its result, without secrets. Of read, the log has only the path and the byte count. The values of each *_headers key, of each key with api_key, apikey, secret or password, of each key that ends with token, and of authorization show as "(hidden)". One summary per turn:

first_sound=1.43s tools=2/3.4s barge_ins=0 outcome=answered

    first_sound (end of speech to first sound) is the main metric. WP2 logs turn, speech, length, end_wait (last speech frame to the end of the turn) and awake per utterance, for example turn=2 speech=2816ms length=3872ms end_wait=608ms awake=true, and a warning when the VAD is slower than real time.     12. Recording for replay¶

    With record_dir, each run writes a directory DIR/YYYYMMDD-HHMMSS/:

    • mic.wav: all mic frames, 24 kHz, without gaps.
    • played.wav: all played sound (earcons and replies), one piece after the other.
    • events.jsonl: one line per gate event and per played piece, with the mic sample at which it happened, for example {"at": 48000, "event": "onset"} and {"at": 96000, "event": "play", "from": 0, "len": 4800}.

    The WAV headers get their lengths at the end; a reader takes a cut file up to its last whole sample. chora-voice gate FILE.wav runs the speech gate of the settings over a file and prints the utterances.

    For replay, a recording directory also holds labels.txt: one label per line, times in s of mic.wav, # starts a comment.

    turn 1.09 2.83   # the user speaks from 1.09 s to 2.83 s
barge 2.08       # the user starts to speak over the agent

    chora-voice replay DIR... runs the gates of the settings over each recording and prints the metrics of section 13. It reads the play lines of events.jsonl and, for the barge-in level, played.wav; a plain clip needs only mic.wav and labels.txt.

    18. ACP sub-agents (WP10, 2026-10-31)¶

    The voice agent manages coding agents that speak the Agent Client Protocol (ACP, https://agentclientprotocol.com): JSON-RPC 2.0 over the stdin and stdout of the agent, one message per line. Module agents.rs.

    • Spawn: one long-lived agent per project, by name. Its command line is sandbox_cmd and agent_cmd, with {dir} and {project} replaced, in the directory of the project, in its own process group. Without unsandboxed: true, coder_cmd and agent_cmd always run in sandbox_cmd (default agent-sandbox.sh: podman per start, project directory mounted, own home, read-only root, all capabilities dropped, network ai-net, ACP on stdio without a tty). The projects: agent_projects and the directories of the inventory; a name matches in any case.
    • Protocol: initialize (protocol version 1, no file system, no terminal), session/new {cwd, mcpServers: []}, session/prompt with one text block, session/update notifications (agent_message_chunk, tool_call, plan; thoughts and the rest are ignored), the request session/request_permission, and the notification session/cancel. Other requests of the agent get "method not found". Prompts to a busy agent wait in a queue.
    • States for mc: starting thinking, ready idle, prompt working, question question, end of turn done, cancelled idle, an error or a stop reason other than end_turn blocked; the end of its process blocked and the phrase agent_ended.
    • Speech: at the end of a turn, its last message is spoken in the voice of the agent (agent_voices in turn, or the voice of agent_start), queued as the coder results: never over the user. At most 8 texts wait; more drop the oldest. A new question of an agent replaces its question that waits, and a question that the agent dropped is not spoken. More than agent_said_chars characters speak the first sentence and phrases.details. The history of the LLM gets the spoken text.
    • Questions: a permission request is spoken as agent_asks ("Atlas möchte notes.txt ändern. Erlauben?": the file name of a path title and a verb for the kind). It waits from when it is spoken, so it also waits while the agent sleeps; the state is confirming. Yes and no words, voice.confirm, or "NAME, ja" answer it; two unclear answers or agent_permission_s without one are a no. Yes picks an allow_once option, no a reject_once one; without a fitting option the outcome is cancelled. A request whose only allowing option is allow_always is spoken as "Atlas wants to edit notes.txt. Always allow?" ("… Immer erlauben?" with reply_language: de), and only then a yes picks allow_always.
    • Routing: the LLM gets agent_list, agent_start {project, name?, voice?}, agent_say {name, text}, agent_stop {name} and agent_status {name?}, and a part of the prompt. agent_start asks first (its confirm rule). An utterance whose first words are the name of an agent goes to it without the LLM: the rest is the prompt, a cancel word cancels its prompt and its queue, a yes or no answers its question. A name word of five letters or more may differ by one edit, a shorter one must be exact ("oder" is not "coder").
    • Events: each change of an agent is voice.state {name, state, task, said, voice, plan, question, log} (log: the last 20 lines of its transcript, › for the user, ⚙ for a tool call, ? for a question); voice.remove {name} when it stops. chora-mc shows the agents in the status line and the agents scene; mc agent.focus shows one agent with its transcript.
    • Logs: $XDG_DATA_HOME/chora/agents/NAME.log, the stderr of the agent and every message (> sent, < received).
    • Lifetime: agent_stop and the end of the voice agent (an error, SIGTERM, SIGINT) send TERM to the process group of each agent and KILL after 5 s. At the end, the voice agent waits until no process of these groups and of the coder runs; a zombie counts as ended. The agents do not survive a restart.

    Tests: tests/fake-acp.sh is a fake agent (plan, tool call, question, long answer); the unit test of agents.rs runs it through a prompt, a yes, the short spoken answer and a stop. Core tests cover the question in the voice of the agent and the address by name.
