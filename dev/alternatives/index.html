    Alternatives¶

    Every part of Void gets a check against existing projects. This page records the first check from October 2026. An entry with the mark unverified needs a second look.

    Compositors¶

    Project Stack Extension model Fit for Void Missing
    River 0.4 Zig, wlroots the window manager is a separate process; it speaks the stable river-window-management-v1 protocol with atomic, frame-perfect updates closest to "the window manager is a plugin" no scene graph, no shaders or effects
    Pinnacle Rust, Smithay gRPC API with Lua and Rust clients; Snowcap widgets best Rust base for a fork: the policy already lives outside the compositor no scene primitives, no shader nodes, no MCP; small team
    niri Rust, Smithay KDL config, niri msg IPC, no plugins best Smithay reference for rendering, shaders, blur and animations scrolling tiling is built in
    cosmic-comp Rust, Smithay none production-grade Smithay reference bound to COSMIC
    Jay Rust, own stack config as a Rust library (unverified) reference for a Vulkan renderer not Smithay; GPLv3
    Wayfire C++, wlroots in-process C++ plugins, IPC close plugin idea, 3D effects unsafe C++ ABI, slow releases
    Hyprland C++, Aquamarine C++ plugins with an unstable ABI, Lua config the target effects opinionated; the plugin ABI breaks with every release
    Mir and MirAL C++ libraries for shells mature C++; the policy model of MirAL
    Louvre C++ library with defaults that can be replaced good scene API not Rust
    scenefx C, wlroots wlroots scene with blur, shadows and rounded corners scene graph and effects C and wlroots only
    CwC, SomeWM, Strata C and Lua, Rust and Lua scripted configs scriptable no policy-free core with a scene graph

    Agent tools exist today only as external MCP servers on top of existing compositors, for example kwin-mcp, and hypruse for Hyprland. The check found no compositor with WASM plugins or built-in MCP. The combination of Void appears to be new: a policy-free core, a scene of primitives with shaders, and one API for plugins, IPC and MCP.

    Options¶

    1. Build on Smithay and copy from others. Sources: the anvil and smallvil examples, niri, cosmic-comp, Pinnacle. This option gives full control of the scene and the plugin model. Recommended (P4).
    2. Fork Pinnacle. A working Smithay compositor with an external API on day one. The fork must remove its policy and add the scene, the shaders and the transactions. R9 proposes a short code review before a decision.
    3. River 0.4 with a Rust window manager. No compositor code, but no shaders, no effects and no scene. This option drops the game-engine half of the idea. It is a fallback for a quick tiling prototype.
    4. An MCP server on an existing compositor, like kwin-mcp. This is the fastest way to try agentic workflows. It gives no canvas and no effects.

    River shows a strong design for the window manager interface. Void can copy its semantics without its code.

    Plugin runtimes¶

    Runtime Strengths Weaknesses
    Extism on wasmtime more than 13 guest languages, simple, sandboxed bytes in, bytes out: every call serializes and copies
    wasmtime with the Component Model typed WIT interfaces, handles to scene nodes, fuel and epoch limits, fast new instances fewer mature guest languages; Rust is first-class
    wasmer works less momentum for the Component Model
    mlua with LuaJIT or Luau low friction, easy reload, Luau sandbox no memory isolation from the host
    Rhai pure Rust, easy slow tree-walking interpreter
    Rune native to Rust not at 1.0
    deno_core (V8) JS and TS ecosystem heavy, GC pauses, API churn
    abi_stable dylibs native speed stale, unsafe unloading, no sandbox
    IPC clients (separate processes) any language, crash isolation from the OS, no runtime in the core a round trip per event; no code in every frame

    For code in every frame, the Component Model is better than Extism. Typed calls only help when the boundary stays typed: JSON over WIT gives back the cost of Extism. R1 proposes to start with IPC clients only and to add wasmtime when a measurement demands it.

    Renderer¶

    • niri, cosmic-comp and Pinnacle use the GLES renderer of Smithay. Custom GLSL shaders through texture and pixel shader elements work in practice, for example the blur of niri.
    • No Smithay compositor renders through wgpu. The Smithay maintainers consider wgpu too abstract for a compositor. Smithay has no merged Vulkan renderer either.
    • Recommendation: GLES and GLSL (P3).

    MCP¶

    rmcp 3.x supports stdio and Streamable HTTP. voidctl mcp uses stdio. A container gets the socket through a bind mount, so Void needs no network transport for now.

    Widgets and shells¶

    Quickshell is the strongest choice: Qt6 and QML, declarative, with live reload. waybar is mature. eww and AGS/Astal need a check of their activity. A webview on gtk4-layer-shell with WebKitGTK, or a Tauri window as a layer surface, shows HTML from agents. All of these need wlr-layer-shell.
