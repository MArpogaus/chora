## 4. Five questions for the architect (Fable)

1. **Should window-management policy (focus, stacking, workspaces/desktops, the cube) become one shared core lib with per-look policy on top?** My evidence says yes for focus, stacking, give/handover state and desktop switching (items 1-3, 16: seven of the top 20 need it, section 2 row 1). Honest limit: mc has no overlapping windows by brief (product-briefs.md:110) and construct shows panes, so for them the shared part is lifecycle and focus, not workspaces. Decide: library in kit (`kit::wm`) with hooks per look, or a plugin (chora-stack, D73)? What is shared mechanism, what stays look policy (tiling tags vs xp desktops vs construct faces)? How does it relate to `kit::book` (lifecycle only, architecture-rc.md:38)?
2. **Cube ownership.** If construct owns the cube and xp/tiling/mc drive it over IPC (backlog.md:174), what is the minimal API (list, switch, turn, pull) and what does an xp user get when construct is not installed or not running? PK4 and the cut gate forbid a hard dependency (architecture-rc.md:57, :66-68), so xp needs an honest fallback. Is mouse-drag turning over IPC fast enough, or does the cube need an input fast path?
3. **Where do desktops live?** Per-look state (as now), in the scene as virtual outputs (D69, design/virtual-outputs.md; D4 "each face runs its own manager", backlog.md:52), or in the cube? This decides items 1, 15 and 16 and whether virtual-outputs steps 8-10 are sprint 2 or later.
4. **Tool, grant and l10n decisions that the plan skips.** One registry for voice tools, system services (B3), grants (A15) and notify, or separate ones? And Fluent (owner, backlog.md:167) or kit tables (architect, architecture-rc.md:146)? Both must be fixed before `kit::actions`, `kit::ask` and `kit::keysheet` freeze their word sets.
5. **Sequence and rework.** Which top-20 items should be built only on the new modules, not before (my candidates: items 5, 11, 12, 13 and the xp cube), and which are safe now (sh-26/27, mc-32 verify, P1, item 19)? Should the WM core come before `kit::book` and `kit::actions` (architecture-rc.md:93-95), or is it designed in sprint 1 and built in sprint 2? What is the config migration promise (old configs still parse, architecture-rc.md:93) when C10 adds `bindings` to xp?
